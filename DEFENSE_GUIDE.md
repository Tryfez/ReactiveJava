## 3. Пункт 2: Параллельные стримы и потокобезопасные коллекции (2.5 минуты)

### Что показать:

### Что сказать:

**Замена стрима:**
"Заменил последовательные стримы на параллельные. Использую `parallelStream()`, который использует ForkJoinPool для распределения задач по потокам (обычно количество потоков = количество ядер CPU)."

**Потокобезопасные коллекции:**
"Для безопасной работы в многопоточной среде использую:
- `ConcurrentHashMap` вместо `HashMap` - потокобезопасная структура данных
- `Collectors.groupingByConcurrent()` вместо `groupingBy()` - использует потокобезопасную коллекцию для параллельной группировки
- Дополнительная синхронизация при обновлении массивов `long[]` в коллекторе через `synchronized` блоки"

**Обоснование:**
"Без потокобезопасных коллекций при параллельной обработке возможны race conditions, потеря данных и `ConcurrentModificationException`. `ConcurrentHashMap` обеспечивает безопасный доступ из нескольких потоков через внутреннюю синхронизацию (CAS-операции)."

**Результаты из вывода:**
- Без задержки: для малых данных (1000-10000) параллельный стрим может быть медленнее из-за overhead на организацию параллелизма (0.33x-0.80x)
- С задержкой: параллельный стрим дает ускорение 4.45x-16.23x, так как задержки выполняются параллельно в нескольких потоках

**Показать пример:**

## 4. Пункт 3: Собственный Spliterator (2 минуты)

### Что показать:
- `Aggregations.java`: класс `ShoeSpliterator` (строки 328-379)

### Что сказать:

**Концепция:**
"Spliterator (Split Iterator) - интерфейс для разделения последовательности элементов на части для параллельной обработки. Собственный `ShoeSpliterator` реализует стратегию разделения списка обуви на подзадачи."

**Реализация методов:**
1. **`tryAdvance(Consumer action)`** - обрабатывает следующий элемент в диапазоне. Если `start < end`, передает элемент в `action` и возвращает `true`.
2. **`trySplit()`** - разделяет текущий Spliterator на две части. Если размер диапазона меньше порога `THRESHOLD` (100 элементов), возвращает `null`. Иначе делит диапазон пополам для балансировки нагрузки.
3. **`estimateSize()`** - возвращает точное количество оставшихся элементов `(end - start)`.
4. **`forEachRemaining(Consumer action)`** - оптимизация: обрабатывает все оставшиеся элементы батчами, что быстрее множественных вызовов `tryAdvance()`.

**Характеристики:**
- `SIZED` - известен точный размер
- `SUBSIZED` - размеры подсплитераторов тоже известны
- `ORDERED` - порядок элементов важен
- `IMMUTABLE` - список не изменяется во время итерации

**Процесс работы:**
"При создании параллельного стрима ForkJoinPool рекурсивно вызывает `trySplit()` до достижения порога разделения. Каждый поток обрабатывает свой диапазон, результаты собираются потокобезопасным коллектором."

**Результаты:**
"Производительность собственного Spliterator сопоставима со стандартным параллельным стримом. На больших данных (50k+ элементов) разница минимальна, что подтверждает, что стандартные реализации в Java уже хорошо оптимизированы."

### Что сказать:

**Ключевые результаты:**
1. **Без задержки:** Для малых данных (1000-10000 элементов) параллельный стрим может быть медленнее из-за overhead на организацию параллелизма. Это связано с тем, что накладные расходы на создание потоков, синхронизацию и координацию работы в ForkJoinPool превышают выгоду от параллелизма при быстрых операциях.

2. **С задержкой:** Параллельный стрим дает ускорение 4.45x-16.23x. Это связано с тем, что задержки выполняются параллельно в нескольких потоках одновременно, а не последовательно. В последовательном стриме задержки накапливаются линейно (N элементов × delay = N×delay), а в параллельном стриме несколько потоков обрабатывают элементы одновременно, перекрывая задержки во времени.

3. **Потокобезопасные коллекции:** Необходимы для корректной работы параллельных стримов. Без них возможны race conditions, потеря данных и некорректные результаты.

4. **Собственный Spliterator:** Позволяет контролировать стратегию разделения данных, но не всегда быстрее стандартного, так как стандартные реализации в Java уже хорошо оптимизированы.

5. **JMH:** Обеспечивает точные и воспроизводимые измерения производительности.

## 7. Возможные вопросы преподавателя и ответы

### В: Почему параллельный стрим медленнее для малых данных без задержки?
**О:** Из-за overhead на создание потоков, синхронизацию и координацию работы в ForkJoinPool. Для малых объемов данных этот overhead превышает выгоду от параллелизма, так как время обработки одного элемента измеряется микросекундами, а overhead составляет миллисекунды.

### В: Как работает ваш Spliterator?
**О:** Spliterator разделяет список на диапазоны индексов. Метод `trySplit()` делит диапазон пополам, если его размер больше порога (100 элементов). ForkJoinPool рекурсивно вызывает `trySplit()` до достижения порога, затем каждый поток обрабатывает свой диапазон через `tryAdvance()` или `forEachRemaining()`.

### В: Почему точка равенства не найдена с задержкой?
**О:** При наличии задержки параллельный стрим всегда быстрее, так как задержки выполняются параллельно в нескольких потоках одновременно. Даже при минимальном количестве элементов overhead параллелизма компенсируется выгодой от параллельного выполнения задержек.

### В: Зачем нужна дополнительная синхронизация массивов в коллекторе?
**О:** `ConcurrentHashMap` защищает структуру Map, но не содержимое массивов. Операции `sc[0] += ...` и `sc[1] += 1` не атомарны, поэтому нужна синхронизация через `synchronized` блок для защиты от race conditions.

### В: Почему собственный Spliterator не всегда быстрее стандартного?
**О:** Стандартные реализации в Java (включая Spliterator для ArrayList) уже очень хорошо оптимизированы командой разработчиков JVM. Собственный Spliterator полезен для специфичных случаев, кастомной логики разделения или обучения, но не всегда превосходит стандартные реализации.
